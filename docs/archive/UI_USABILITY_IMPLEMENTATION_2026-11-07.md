# UA-Cast: практичність інтерфейсу та вимірювання продуктивності

Дата: 2026-11-07. Реалізація погоджених змін головного екрана, форми джерела,
файлового плеєра, трансляції та оформлення. Xiaomi TV і фізичні телефони не використовуються.

## Що змінено

- Одне джерело на головному екрані замість дублювання у двох великих блоках.
  Статистика, кеш і телегід розкриваються через «Докладніше». Нещодавній канал,
  обране, перегляд каналів і локальне відео збережені. Місце реклами залишається після основних дій.
- Телегід розрізняє відсутність джерела, очікування, завантаження, готові дані та помилку.
  Невдала спроба оновлення не ховається за старим кешем. Є перехід безпосередньо
  до редактора телегіда та повторення невдалого завантаження налаштованого джерела.
- «Вставити посилання» читає текст буфера лише після натискання. Результат асинхронного
  читання не перезаписує новий ручний ввід; об’єкти/URI буфера не завантажуються.
  Назва плейлиста необов’язкова й схована під «Додатково». Для наявних джерел пояснення коротше.
  Нова форма не успадковує назву активного джерела; лічильник редагувань захищає також
  від сценарію «ввести й стерти текст до завершення читання буфера».
  Валідація, блокування повторного імпорту, попередження HTTP і обмеження Xtream збережені.
- Файловий плеєр має компактну назву й кнопки −10/+10 секунд. Перемотування обмежене
  тривалістю та можливістю seek; невідома тривалість і віддалений власник керування не обходяться.
  Швидкі повторні натискання рахуються від актуальної позиції Media3, а не від знімка UI.
  Звичайну дубльовану нижню кнопку «Назад» прибрано; вихід із помилки збережено.
- DLNA позначений «Інші ТВ». Chromecast зберіг стандартну кнопку та діалог SDK.
  Ім’я підключеного пристрою й зупинка трансляції доступні в плеєрі. Ім’я Cast живе
  стільки, скільки SDK-сесія, навіть якщо завантаження медіа завершилося помилкою.
- Світла тема телефона з контрастним синім акцентом. Плеєр і TV залишаються темними.
  Перемикання палітри не демонтує композицію плеєра. Системні значки враховують видимий екран;
  Android 7.0/7.1 з білими навігаційними кнопками отримує чорне тло панелі навігації.
- Менше рамок і декору в налаштуваннях, діалог вибору теми замість чотирьох тісних сегментів.
  Нові тексти перекладені українською, англійською, іспанською та російською.
- Режим зменшених ефектів вимикає декоративний нескінченний рух, шпалери, світіння фону й тіні.
  На слабких пристроях він автоматичний до явного вибору користувача. Системне вимкнення
  анімацій зберігає пріоритет. Налаштування спостерігає лише окрема область оформлення.

## Вимірювання

Попередній `firstPlayerLaunch` відкривав порт 9 на localhost: реального декодування відео не було.
Тепер лише benchmark-варіанти містять маленьке оригінальне синтетичне H.264-відео.
Звичайні debug/release/Play APK його не містять. Тести очікують `onRenderedFirstFrame`,
перевіряючи URI поточного медіа, а не тільки `playWhenReady`, READY або кнопку fullscreen.
Власник видаляє слухача й завершує trace під час знищення.

До існуючих восьми сценаріїв додані перемикання каналу, пошук серед 40 000 каналів і прокрутка.
Для першого кадру та перемикання додані trace-бюджети 5000 мс; старі межі не послаблені.
Trace вимірює час від MediaItem transition до кадру: він не включає всю затримку натискання,
мережі провайдера або debounce перемикання. Синтетичний локальний файл ізолює декодування/UI.

Окремий скрипт збирає PSS усього процесу та Java/native/graphics під час benchmark.
Максимум вибірки є нижньою межею миттєвого піку; PSS не дорівнює malloc/кількості алокацій.
Ці категорії не змішуються з `memoryHeapSizeMaxKb`. Нові абсолютні межі PSS слід
встановлювати за повторюваними вимірюваннями, а не вигадувати відсоток прискорення.

## Перевірки та межі висновку

Підсумковий стан: функціональні перевірки пройшли; performance gate поки не зелений.
Три сценарії перевищують незмінений бюджет P95 CPU-часу кадру 100 мс.

| Перевірка поточного коду | Результат |
| --- | --- |
| Debug unit/Robolectric/screenshot | 2883 тести, 0 помилок, 0 пропусків |
| Вибрані критичні Release-тести | 588 тестів, 0 помилок, 0 пропусків |
| Вибрані критичні Play-тести | 588 тестів, 0 помилок, 0 пропусків |
| Native UI/плеєр/lifecycle, API 36 | 35 тестів, 0 помилок; 45 приватних файлів відновлено з перевіркою хешів |
| Macrobenchmark, API 30 | 12 інструментальних тестів виконано, 11 вимірюваних сценаріїв; 3 перевищення бюджету |
| Detekt | Успішно; baseline порожній |
| Lint Debug і Play | 0 errors, 0 warnings; по 2 інформаційні hints |
| Python: валідатор бюджетів / PSS-парсер | 10 / 5 тестів, успішно |

Release/Play перевірки вище є вибраними наборами, а не всією Debug-матрицею. Однакові
тести в різних варіантах не слід рахувати як незалежні унікальні сценарії. У фінальних
crash-буферах API 36 та API 30 записів про аварії немає. Це не замінює моніторинг ANR/витоків.
1224 файли реалізації, тестів, еталонів і конфігурації звірено з хешами після прогонів.

### Числа продуктивності

Основний ізольований прогін: Windows, Android 11/API 30 x86_64, 2 ядра, 2048 MiB RAM,
1080×1920, програмний GLES SwiftShader. Runtime `heapgrowthlimit=192m`, `heapsize=512m`;
це не фізичний слабкий телефон і не контрольований Linux CI runner. Старі бюджети не змінені.

| Метрика | Результат | Межа |
| --- | --- | --- |
| Холодний старт, median initial display | 805 мс | 5000 мс |
| Теплий старт, median initial display | 149 мс | 2500 мс |
| Холодний старт із 40 000 каналів, initial display | 800 мс | 10 000 мс |
| Відкриття 40 000 каналів, P95 CPU frame | **122 мс** | **100 мс — перевищено** |
| Перший запуск плеєра, P95 CPU frame | **234 мс** | **100 мс — перевищено** |
| Перехід у fullscreen, P95 CPU frame | **145 мс** | **100 мс — перевищено** |
| Перший відеокадр, median trace | 284 мс | 5000 мс |
| Кадр після зміни каналу, median trace | 290 мс | 5000 мс |
| Перемикання каналу, P95 CPU frame | 53 мс | 100 мс |
| Пошук серед 40 000 каналів, P95 CPU frame | 12 мс | 100 мс |
| Прокрутка великої групи, P95 CPU frame | 32 мс | 100 мс |
| Відкриття EPG, P95 CPU frame | 77 мс | 100 мс |
| XMLTV 350 000 програм: parse + index, median trace | 1559 мс | 60 000 мс |
| Найбільший `memoryHeapSizeMaxKb` серед сценаріїв | 90 029 KiB | 262 144 KiB |

Initial display не є часом завершення всього відновлення джерела. Trace першого кадру
не є наскрізною затримкою від натискання користувача й не перевіряє мережу провайдера.

Контрольні повтори тих самих трьох сценаріїв без PSS-семплера:

| P95 CPU frame | SwiftShader без семплера | Host GPU NVIDIA RTX 5070 без семплера |
| --- | --- | --- |
| Відкриття великого плейлиста | 125 мс | 51 мс |
| Перший запуск плеєра | 252 мс | 57 мс |
| Fullscreen | 135 мс | **166 мс** |

Отже, перші два перевищення залежать від графічного backend емулятора; сам семплер
їх не пояснює. Fullscreen не вкладається в межу й на host GPU. Зміна GPU не є
прискоренням коду. Наступний крок — повторити на сталому Linux CI runner і профілювати
перехід fullscreen на фізичному пристрої, перш ніж змінювати власність Surface чи lifecycle.
Зменшення бюджету перевірки або розтягування вимірювання для приховування P95 не робилося.

PSS: 202 валідні вибірки; 88 разів процес був недоступний між benchmark-запусками;
5 помилок читання. Вибіркові максимуми Java 74 976 KiB, native 130 492 KiB,
total 213 715 KiB (208,7 MiB). Максимуми категорій не обов’язково одночасні.
Graphics PSS у цьому емуляторі був 0; це не доказ нульових GPU-витрат на реальному телефоні.

### Докази та збірка для перевірки

Локальний каталог `build/usability-2026-11-07/` містить:

- `verified-evidence.json`, `verification.log`, `source-fingerprint.json` — звірка результатів і коду;
- `verified-gates.log`, `detekt-verified.log`, `python-tests.log`, `architecture-checks.log`;
- `emulator-regression.log`, `native-verified-run.log`, `native-screens/` — native UI та lifecycle;
- `performance-final/`, `performance-api30-run.log`, `performance-budgets.log` — повний вимір;
- `performance-no-sampler/`, `performance-host-gpu/` — окремі діагностичні повтори;
- `process-memory-api30.json` — PSS із лічильниками доступності й помилок;
- `artifact-verification.log` — 15 native-бібліотек, 6 ліцензій, актуальні legal HTML у Debug APK;
- `UA-Cast-usability-debug-universal.apk` — окрема Debug-версія `com.uacastplayer.debug`,
  0.9.7 (164), 39 653 628 bytes, ABI arm64-v8a / armeabi-v7a / x86_64.

SHA-256 APK: `dc35cc5465d5d348c0c4800c55eab6e1d398bd54db106181e313e9014281dea5`.
Це тестова збірка, не підписаний production-реліз для розповсюдження. Вона не містить
синтетичного benchmark-відео чи вбудованих плейлистів. Старий Play AAB перевірений лише
на пакування ліцензій/native/legal assets; він не є новим релізом цих UI-змін.

Нові тести перевіряють EPG-стани та прямий перехід у налаштування, читання буфера з
конкурентним редагуванням, нову назву джерела, накопичення seek, відкидання старого
first-frame callback, збереження Cast receiver name, палітри/контраст, незмінність
плеєра при зміні теми, геометрію вузького екрана та шрифт 200%.
Native accessibility-стан кадру виставляється безпосередньо на Android View:
Compose semantics сам по собі не експортував його в UiAutomator. Це перевірено на API 30/36.

Проміжні збої нових тестів і кодування допоміжного скрипта усунено до фінального прогону.
Кодування відновлене точним зворотним перетворенням; змінені еталони переглянуті перед
оновленням. Перевірки геометрії та бізнес-умов не послаблювалися.

Workflow performance gate підготовлений локально; GitHub CI у цій роботі не запускався.
Baseline profile не регенеровано: вимірювання використовують наявний профіль.
Створені для цієї роботи емулятори завершені; комп’ютер, телефони й Xiaomi TV не вимикалися.

Ця робота не підтверджує сумісність Hisense VIDAA або доступність Google Play Billing.
Юридичні прапорці й дозволи на публікацію релізу не змінені. Відсутність помилок у прогоні
не є доказом відсутності всіх помилок застосунку.

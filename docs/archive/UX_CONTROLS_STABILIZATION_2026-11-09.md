## Поведінка та межі змін

Undo зберігає один останній запис, включно з часом додавання, адресою, заголовками та метаданими.
Відновлення використовує актуальний список і сусідні ключі. Застаріла дія не повертає видалений
канал поверх новішого запису; імпорт/повна заміна списку скасовує попередню дію.
Стан належить репозиторію/ViewModel. Snackbar використовує доступний системі Material3 timeout;
окремого таймера чи фонового scope немає. Undo не є довготривалою історією після смерті процесу.

TV зберігає ключ та індекс вибраного каналу. Після повернення вибирає той самий канал або
найближчу допустиму позицію, якщо його вже немає. Прокручування виконується лише коли ціль
за межами видимих карток. Введення пошукового запиту не відбирає фокус у поля.

Пульт показує фактичну адресу, оскільки чинний захищений протокол не передає назви моделі TV.
Згортання закриває лише діалог. Повторне відкриття активного з’єднання не вимагає нового коду.
Кнопка «Від’єднати», Back/закриття та перехід застосунку у фон зберігають явне завершення
з’єднання; приховану фонову службу не додано. Протокол та криптографія не змінювалися.

При порожньому запиті Обране використовує незмінний snapshot списку без повторного копіювання.
Нові UI-компоненти використовують наявні кольори теми. Постійних анімацій або додаткового
опитування мережі немає. Створення, власник і звільнення Media3 player не змінені.

## Перевірка fullscreen

На власному API-30 емуляторі, 2 CPU / 2048 MB / host GPU, виконано по 5 ітерацій.
Це локальний діагностичний запуск; CI використовує окремо заданий software renderer, тому
ці результати не видаються за успішний CI performance gate.

## Розслідування proxy timeout

Два desktop stress-прогони по 40 JUnit cases з цільовим обсягом 10 000 сегментів відтворили
по одному таймауту; кожен невдалий case зупинявся на збої, без retry.
Діагностика другого: activeClients=0, черги не відхиляли запитів, серверний socket FIN_WAIT_1,
клієнтський ESTABLISHED. Працівники вже чекали нової роботи; зависання в handler не виявлено.

Окрема WindowsLoopbackProbe.java використовує лише стандартний JDK ServerSocket/Socket,
два flush та close, без залежностей UA-Cast. Вона відтворила таймаут після 439 успішних
відповідей: прийнято 57 байтів заголовків, тіло/EOF не прийшли за ті самі 5 секунд.
Це доводить, що такий збій не потребує коду proxy. Межа між причиною у Windows, JDK або
локальному мережевому оточенні ще не встановлена; це не підстава оголошувати всі proxy-баги
неможливими чи міняти його робочу поведінку навмання.

На Android API 30 той самий lease stress перевірив усі 10 000 повних тіл відповідей успішно.
Наявний JVM-тест посилено перевіркою точного тіла, додано failure-only діагностику та
Android stress-тест. Таймаут 5000 ms не збільшувався, retry/skip не додано.

Докази: proxy-stress.log, proxy-diagnostic-driver-build.log, windows-jdk-only-probe.log,
WindowsLoopbackProbe.java, proxy-native-api30.log у build/ux-controls-2026-11-09/.

## Остаточні перевірки

Проміжний lint виявив ModifierFactoryExtensionFunction у новому TV helper. Виправлення
використовує Modifier.tvBrowseFocus і зберігає ланцюжок модифікаторів; suppression не додано.
Після цього повторно запущені повний gate та всі 89 Android-сценаріїв на новому APK.
Попередні перервані запуски не зараховуються як успішна остаточна регресія.
Остаточна Android-регресія: **89/89 PASS**, 0 failures, 0 errors, 0 ignores/assumption skips.
У ній: 8 local-video, 16 UI, 16 player-lifecycle, 1 remote-header flow, 4 TV-focus,
4 remote-lifecycle та 40 proxy stress cases. Останні перевіряють 10 000 точних тіл сегментів.
Android 11 / API 30, власний емулятор; стан debug-застосунку відновлено. Crash buffer порожній.
Прогін тривав 841.017 s і є функціональною перевіркою, не performance benchmark;
для розбору довгого Espresso-очікування знято короткий JDWP snapshot з від’єднанням debugger.
Цикли згортання/відкриття завершилися успішно. Нативні знімки Undo до/після recreation
переглянуті: snackbar розташований над мініплеєром і навігацією, перекриття немає.

Код, тести, еталони, конфігурація та скрипти зафіксовані у final-source-fingerprint.json.
Фінальний APK і числові підсумки звіряються саме з цим snapshot.

Повний Gradle gate завершився успішно за 9m 59s: 2905 app unit/screenshot, 133 core та
5 decoder tests, без failures/errors/skips. Lint застосунку Debug/Release/Play має 0 помилок
і 0 попереджень; detekt app/core — 0 findings, baseline порожній, архітектурні межі перевірені.

Lint незміненого decoder-модуля має 0 помилок і 7 попереджень: 2 GradleDependency та
5 UseTomlInstead. Це пропозиції оновлення annotation-залежностей/каталогу версій, не
виявлені падіння декодера. У benchmark-збірці також лишаються 2 повідомлення R8 про
відсутність async parsing у ClassFileResourceProvider інструментарію. Версії залежностей
і правила lint не змінювалися для приховування цих повідомлень.

## Що залишається

1. Доведене прискорення fullscreen без зміни budget; стабільний повтор вимірювань.
2. Фізичні TV/телефон: end-to-end сполучення та керування через домашній Wi-Fi. Цього разу
   використовуються лише власний емулятор і керована TV presentation, не фізичний Xiaomi TV.
3. Перевірка на Linux CI для незалежності від відтвореного Windows/JDK loopback-збою.
4. Наявні зовнішні legal/commerce release approvals не закриваються змінами UI. Production
   release, новий номер версії та публікація GitHub у цьому етапі не виконуються.

Після відновлення даних і збереження доказів завершено тільки власний тестовий емулятор.
